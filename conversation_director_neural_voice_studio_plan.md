# Conversation Director & Neural Voice Studio
## Full Implementation Plan for a Model-Agnostic, GPU-Accelerated Radio Voice System

**Target platform:** DGX Spark as the primary GPU inference/refinement server  
**Primary use case:** two or more LLM-driven radio personalities, hosts, guests, and callers with highly configurable, natural, expressive, human-like voices  
**Core principle:** separate *what is being said*, *who is speaking*, *how it is performed*, and *how it is broadcast* into independent layers so any TTS or voice model can be swapped without redesigning the system.

---

# 1. Product Vision

Build a local-first **Conversation Director + Neural Voice Studio** that takes text generated by arbitrary LLMs, passes it through any supported TTS backend, and then performs a second GPU-powered voice-refinement pass that controls delivery, cadence, emotion, prosody, timing, human imperfections, voice character, and final broadcast treatment.

The system must also function as a **voice laboratory**. It should accept authorized audio/video reference material, including user-supplied files and supported video links, extract transcripts and measurable vocal-style characteristics, visualize those characteristics, and let the operator recombine them into new synthetic voice personas.

The system should make a strong architectural distinction between:

1. **Speaker identity** — the acoustic traits that make a real person recognizable.
2. **Performance style** — cadence, pace, pitch movement, hesitation, intensity, stress, pause structure, articulation, breathiness, and other style traits.
3. **Conversational behavior** — interruptions, turn-taking, emotional response, laughter, confusion, stuttering, backtracking, excitement, tension, dominance, rapport, and other interaction-level behavior.
4. **Broadcast processing** — EQ, compression, saturation, de-essing, proximity effect, limiting, ambience, telephone/radio coloration, and loudness.

This separation is essential.

The system should be capable of producing voices that feel coherent and human without requiring a specific TTS model.

# 2. Safety, Rights, and Provenance Architecture

The product should be built around two distinct reference modes.

## 2.1 Style Reference Mode

A user may supply a public or private audio/video reference and extract **non-identifying performance characteristics** such as:

- average speaking rate
- local speaking-rate variance
- pause density
- pause duration distribution
- pitch range
- pitch contour statistics
- pitch-change velocity
- volume dynamics
- stress patterns
- sentence-final intonation
- disfluency frequency
- hesitation patterns
- articulation density
- syllable timing
- breath placement
- laugh placement
- conversational overlap behavior
- response latency
- vocal energy
- perceived expressiveness

These should be converted into a reusable **Style Vector** that does not require preserving the original person's recognizable voice identity.

This enables the desired "simulacrum" workflow: study a performance, extract its mechanics, then use those mechanics to build a new synthetic caller.

## 2.2 Identity Clone Mode

Recognizable voice cloning must be a distinct capability with explicit authorization/provenance requirements.

A voice identity record should include:

```yaml
identity:
  id: voice_023
  display_name: "Studio Voice 23"
  source_type: uploaded_recording
  authorization:
    status: verified
    scope: local_generation
    expires: null
  provenance:
    source_asset_ids:
      - asset_a31
      - asset_a32
```

Do not silently convert every YouTube reference into a recognizable clone.

For public-video material where identity-cloning authorization is absent, the default workflow should be:

```text
Reference audio
      ↓
Style analysis
      ↓
Identity-discarding style representation
      ↓
Synthetic base voice
      ↓
Performance transfer
      ↓
New simulacrum voice
```

This still provides the exploratory studio the project requires while reducing accidental impersonation.

## 2.3 Output Provenance

Every generated asset should retain machine-readable metadata:

```yaml
generation:
  synthetic: true
  voice_identity_id: synthetic_104
  style_sources:
    - style_018
    - style_026
  engine: refiner_v3
  created_at: 2026-08-12T13:00:00Z
```

For exported audio, optionally embed provenance metadata in WAV/BWF/iXML or a sidecar JSON file.

# 5. Internal Audio Standard

Normalize all engines to a common internal audio contract.

Recommended internal format:

```yaml
audio:
  encoding: float32_pcm
  sample_rate: 48000
  channels: 1
  layout: mono
  chunk_ms: 20
```

TTS adapters may produce 22.05, 24, 32, 44.1, or 48 kHz audio.

Immediately after TTS:

```text
Model output
    ↓
decode
    ↓
resample
    ↓
normalize channel layout
    ↓
48 kHz float PCM
```

Do not let downstream systems know or care what sample rate the original TTS model produced.

# 8. Conversation Director

The Director should operate above the TTS level.

Its job is to determine **performance intent**, not synthesize audio.

## Inputs

```text
speaker profile
conversation transcript
last N turns
current utterance
topic
relationship state
conversation momentum
speaker emotional history
external radio-show state
```

## Outputs

```text
performance vector
turn-taking instructions
overlap instructions
response latency
optional paralinguistic events
broadcast-scene changes
```

## Conversation State

Maintain a global state object:

```yaml
conversation:
  topic_seriousness: 0.31
  humor: 0.62
  momentum: 0.74
  conflict: 0.08
  awkwardness: 0.11

relationship:
  host_a_host_b:
    rapport: 0.79
    familiarity: 0.91
    tension: 0.06
    dominance_balance: -0.12
```

Each speaker should also maintain state:

```yaml
speaker_state:
  energy: 0.58
  amusement: 0.36
  confusion: 0.04
  agitation: 0.02
  fatigue: 0.10
```

States should decay naturally rather than reset every utterance.

# 9. Human Performance Behavior

The project should explicitly support human imperfections.

These should not be inserted as independent random effects.

They should be generated from correlated behavioral states.

## Example: Flustered

```text
pace                  +15%
pitch variation       +20%
pause predictability  -30%
self-correction       +40%
false starts          +30%
breathing rate        +18%
sentence completion   -15%
```

## Example: Confused

```text
response latency      +25%
hesitation            +45%
question intonation   +30%
sentence restart      +20%
pace                  -8%
```

## Example: Angry / Blustering

```text
intensity             +25%
pace                  +10%
consonant attack      +15%
interruptions         +30%
pause length          -20%
pitch range           +15%
```

## Example: Exhausted

```text
pace                  -15%
pitch range           -25%
breathiness           +15%
pause duration        +35%
articulation          -10%
```

## Example: Nervous

```text
pitch                  +5%
pitch instability      +20%
hesitation             +25%
filler words           +18%
micro-pauses           +30%
```

The UI can expose these as named macro states while still letting advanced users edit underlying parameters.

# 10. Neural Voice Refiner

This is the key GPU-powered secondary engine.

Do not design it as a single required model.

Instead implement a **capability graph**.

```text
RAW SPEECH
   │
   ├─→ timing/prosody transform
   │
   ├─→ optional neural re-performance
   │
   ├─→ optional authorized identity conversion
   │
   ├─→ spectral repair
   │
   ├─→ artifact cleanup
   │
   └─→ output normalization
```

Each backend declares capabilities:

```json
{
  "name": "backend_x",
  "capabilities": [
    "voice_conversion",
    "emotion",
    "pace",
    "pitch",
    "prosody"
  ]
}
```

The Refiner compiles requested controls into an execution graph.

If the current model cannot directly control a requested parameter, use:

1. another neural backend,
2. deterministic DSP,
3. timing manipulation,
4. text-level performance modification,
5. or a no-op with telemetry.

Never silently fail.

# 11. Backend Adapter Interface

Every model should implement a shared interface.

```python
class VoiceBackend:
    def capabilities(self) -> set[str]:
        ...

    def load(self) -> None:
        ...

    def unload(self) -> None:
        ...

    def process(
        self,
        audio,
        controls,
        reference=None,
        stream=False
    ):
        ...
```

TTS interface:

```python
class TTSBackend:
    def synthesize(
        self,
        text,
        speaker,
        controls,
        stream=False
    ):
        ...
```

This prevents the application from becoming tied to Piper, Fish Speech, Chatterbox, OpenVoice, or any future model.

# 12. Candidate Model Backends

The implementation should benchmark rather than permanently commit to a single model.

Potential backends include:

- **Piper** — lightweight baseline / emergency fallback / low-latency CPU TTS.
- **Chatterbox** — candidate expressive TTS and voice-conversion backend.
- **OpenVoice** — candidate tone-color and style-transfer backend.
- **Fish Speech / Fish Audio S2 family** — candidate high-quality neural speech backend, subject to local model/license requirements.
- Additional future voice conversion, speech editing, diffusion, or codec-language models.

These belong behind adapters.

The system itself must survive the replacement of every one of them.

# 15. YouTube Transcript / Caption Workflow

The desired workflow:

```text
Paste YouTube URL
       ↓
Retrieve metadata
       ↓
Detect available caption tracks
       ↓
Use caption/transcript source when authorized/available
       ↓
Otherwise transcribe user-authorized audio locally
       ↓
Normalize timestamps
       ↓
Speaker diarization
       ↓
Markdown transcript
```

YouTube's official API exposes caption-track metadata and caption operations, but actual caption downloads are authorization-sensitive. Therefore the application should support multiple compliant ingestion strategies rather than assuming every public video's captions can always be downloaded through the official API.

Markdown transcript format:

```markdown
# Source Transcript

**Source:** Example Video  
**Duration:** 18:42

## 00:00:00 – Speaker 1

This is the first section of speech.

## 00:00:07 – Speaker 2

This is another section.
```

Also produce machine-readable JSON:

```json
{
  "segments": [
    {
      "start": 0.0,
      "end": 7.2,
      "speaker": "speaker_01",
      "text": "..."
    }
  ]
}
```

# 18. Voice Analysis Engine

Every selected reference segment should be analyzed at several levels.

## Acoustic

- F0 / pitch contour
- pitch distribution
- pitch range
- pitch slope
- intensity envelope
- spectral centroid
- harmonicity
- jitter-like measures
- shimmer-like measures
- breath/noise ratio
- formant estimates where useful

## Temporal

- words per minute
- syllables per second
- phoneme duration
- pause duration
- pause frequency
- pause placement
- inter-word gaps
- acceleration/deceleration
- phrase length

## Prosodic

- stress placement
- emphasis
- sentence-final contour
- question contour
- phrase boundary patterns
- pitch-reset behavior
- rhythm regularity

## Behavioral

- filler-word rate
- repetitions
- false starts
- stutter-like repetitions
- self-corrections
- sentence abandonment
- laughter
- sighing
- breath events
- overlap / interruptions

## Conversational

When multiple speakers are present:

- response latency
- interruption tendency
- overlap duration
- turn length
- turn-taking rhythm
- accommodation to the other speaker
- energy matching
- pace matching

# 20. The Spiral Voice Visualization

The studio's signature visualization should be a manipulable **Voice Spiral**.

The spiral represents a voice's multidimensional performance signature.

Concept:

```text
                    energy
                      ▲
               ╭──────●──────╮
          pitch●              ●authority
              ╱                ╲
       rhythm●                  ●warmth
              ╲                ╱
         pause ●              ●texture
               ╰──────●──────╯
                    cadence
```

But visually it should be a real 3D or 2.5D spiral rather than a radar chart.

## Suggested Mapping

Map the spiral longitudinally to time.

```text
spiral axis = time
radius = vocal energy
vertical deviation = pitch
local thickness = intensity
twist rate = cadence
surface roughness = texture/rasp
node density = syllable density
gaps = pauses
color dimension = categorical emotion
```

If using a strict no-color accessibility mode, emotion can additionally be represented with texture or marker shape.

## Interaction

Users should be able to:

- rotate
- zoom
- scrub through time
- select a portion
- drag nodes
- widen pitch range
- compress rhythm
- smooth cadence
- increase hesitation
- reduce regularity
- exaggerate expressive peaks
- pluck sections from one signature
- merge them with another
- audition immediately

# 28. Disfluency Engine

Create a dedicated representation.

```yaml
disfluency:
  filler_probability: 0.08
  restart_probability: 0.04
  repetition_probability: 0.02
  stutter_probability: 0.01
  incomplete_sentence_probability: 0.03
  correction_probability: 0.04
```

The system must decide where disfluencies occur using linguistic boundaries.

Avoid naïvely inserting `"uh"` randomly.

Use positions such as:

```text

after interruptions
during uncertainty
before corrections
at topic transitions
after emotional spikes
```

# 29. Stutter Modeling


# 30. Emotional State Engine

Create an emotion state vector.

```yaml
emotion:
  amusement: 0.10
  anger: 0.00
  fear: 0.00
  embarrassment: 0.00
  sadness: 0.00
  excitement: 0.15
  confusion: 0.02
  affection: 0.18
```

Apply inertia:

```text
new_state =
old_state × persistence
+
event_response × sensitivity
```

This avoids a speaker becoming furious for one sentence and completely neutral on the next.

# 33. Streaming Architecture

A radio show cannot wait for full clips to finish rendering.

Use chunked synthesis.

Target:

```text
LLM token stream
   ↓
sentence / phrase segmenter
   ↓
TTS chunk generation
   ↓
refiner streaming queue
   ↓
DSP
   ↓
jitter buffer
   ↓
playback
```

Start synthesizing after a stable phrase boundary rather than waiting for the whole response.

# 106. Design Principle: Never Lose the Original

For every generation retain:

```text
original text
raw TTS
performance vector
refined audio
broadcast audio
```

This makes A/B testing and debugging possible.

The operator should always be able to return to the unprocessed voice.

---

# 107. Design Principle: Meaning Before Effects

Human behavior should originate from conversation context.

Preferred:

```text
conversation meaning
   ↓
emotional/performance state
   ↓
linguistic behavior
   ↓
vocal behavior
```

Avoid:

```text
audio
 ↓
random "human" effects
```

The former creates characters.

The latter creates gimmicks.

---

# 108. Design Principle: Style is a First-Class Asset

Do not treat extracted reference style as a hidden model embedding only.

A style must be:

```text
inspectable
editable
versioned
layerable
blendable
auditionable
exportable
traceable
```

The Voice Spiral is the visual interface to this asset.

# 109. Design Principle: Identity and Style Remain Separate

This is one of the most important constraints in the entire project.

```text
IDENTITY
Who the voice acoustically resembles

STYLE
How the person performs speech
```

A user should be able to choose:

```text
Synthetic Identity #4
+
Style Reference #17
```

without creating an imitation of Reference #17's recognizable voice.

Authorized identity cloning can be added independently.

# 111. Current Backend/Platform Notes

At implementation time, benchmark current releases rather than relying on fixed assumptions.

Relevant upstream projects and documentation to evaluate include:

- Resemble AI Chatterbox: https://github.com/resemble-ai/chatterbox
- MyShell OpenVoice: https://github.com/myshell-ai/OpenVoice
- Fish Audio / Fish Speech: https://github.com/fishaudio/fish-speech
- YouTube Data API caption resources: https://developers.google.com/youtube/v3/docs/captions

OpenVoice's published project description specifically emphasizes tone-color cloning and style controls including emotion, rhythm, pauses, and intonation, making it relevant to the adapter/refinement experiments.

Current Fish Speech documentation describes high-VRAM local inference for its latest model family, which makes the DGX Spark an appropriate machine on which to benchmark that class of backend.

The YouTube Data API exposes caption-track resources, but actual caption download behavior is authorization-sensitive; therefore the application should retain both caption-provider and local-ASR paths rather than designing around guaranteed public-caption download.
