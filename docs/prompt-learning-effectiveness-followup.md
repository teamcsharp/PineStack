# Rejection learning effectiveness follow-up

The deployed learner was collecting evidence but had no mechanism to learn whether its advice worked. Its twelve original hints remained unchanged for about 8.4 hours. This does not establish that every new rejection was correct or that every rewrite failed; the available learner data had no successful-attempt denominator.

## Read-only evidence before the change

`prompt-learning-effectiveness-status.json` records the authenticated GET at 1788838274.78: enabled, fluid, revision 2, unchanged since 1788808056.97, no learner errors, 1,935 retained observations. A subsequent consistent read-only SQLite transaction found 1,940 observations covering 652 distinct kind/source pairs, of which 316 had eligible machine-failure evidence. There were **zero individual decisions** in the learner's decision table. The user-visible rejection count, immutable occurrences, repeated attempts and distinct original sources are different quantities.

The concrete defects were:

1. **Permanent incumbents and global starvation.** `PromptLearningStore._choose` put all still-eligible incumbent hints first and stopped at twelve. The pure selector reproduced exactly the original twelve despite 34 currently eligible patterns. Twenty-two eligible patterns could not enter. News and SFX Guy had no hints at all: news rhyme had 20 distinct sources / 9 parents, SFX rhyme 10 / 10, and manager rhyme 17 / 8. Gallery's quantity, name and question failures were also excluded despite substantial current evidence. See `prompt-learning-effectiveness-analysis.json`.
2. **Repeated advice without outcome credit.** Only refusals and individual decisions call the original `observe` / `decision` paths. There was no successful-attempt table, strategy exposure, model/profile cohort, first-pass denominator or linked-repair result. Gallery rhyme support increased from 9 to 88 sources and anchor support from 8 to 77 without changing either reminder. The existing catalog mostly repeated requirements already present in `crystal_prompts._frame`; it did not test a different procedure.
3. **Old fault support survives a changed attempt.** `_summarize` previously chose the latest source separately within each fault family. Thus an earlier quantity failure still voted for quantity advice after a later attempt had different faults. The read-only analysis found 112 such older-pattern support pairs. A later absence of that fault is not proof of a successful rewrite; it is evidence that the older fault is no longer the latest measured failure for that source.
4. **Selection failure reached actual prompts.** The retained trace snapshot contains 3,457 effective-rule steps at learning revision 2. All 193 news steps and all 143 SFX Guy steps had empty learned guidance. For example, news trace `071fc3d775c740829092b5b6ce557d5d`, step 29397, at 1788838361.01 has revision 2 and zero learned-guidance characters. Gallery's latest example still contains the same three reminders. See `prompt-learning-effectiveness-traces.json`. Trace steps repeat within attempts and cannot be used as a success-rate denominator.
5. **Eligibility exclusions and compatibility are distinct from selection.** The API reported 364 unsupported-gate observations, 33 without a known parent, 15 technical, one old/unknown grader, five without verified machine failure, and eight without a specific catalog pattern. Unknown parents and technical events must not be turned into invented training labels. Grader version 5 eligibility alone also does not identify the exact model, prompt, profile or contract used; comparisons require those versions explicitly.

The read-only work used a GET snapshot, read-only SQLite transactions, the consistent retained trace export under `data/rejection_followup_audit/1788838388`, and a pure selector replay. No live votes, settings changes, model calls or playback controls were issued.

## Implemented bounded replacement

`prompt_learning.py` now budgets four hints **per supported kind**, with a maximum 1,000-character runtime selection. Current distinct-source support can replace incumbents, with a modest hysteresis margin to avoid revision churn on one additional observation. The latest immutable occurrence's fault families replace older votes from that source. Counter-only changes leave the effective revision stable.

`selection(kind)` returns the exact `guidance`, `strategy_ids` and `learning_revision` to pin before a model request. `outcome(row)` records a stable request/turn attempt ID, source and parent hashes, kind, actual model, profile fingerprint, prompt/contract/grader versions, derived source-length band, first/repair stage, prior attempt link, used strategies, raw/effective grade results and factual/rhyme/fault-family results. It neither evaluates text nor changes acceptance thresholds. Technical, deferred, preview, imported and read-time regrade observations do not train it. Duplicate attempts are idempotent; changed evidence under one ID conflicts.

The immutable body also binds the candidate wording by hash. Overall first/repair attempt counts include successes with **no selected strategy**, while strategy comparisons separately deduplicate sources. A durable per-pattern recipe history preserves exhausted state through active-hint eviction, restarts and outcome-retention rollover. Meaning-grade rhyme classification follows the authoritative bar report, so an advisory spelling-rhyme miss cannot falsely become a rhyme-learning failure when the actual bar check passed.

Classifier version 2 can replace older **derived** patterns and exclusions only when the original source/candidate/parent hashes, occurrence, kind, gate and grader are unchanged. Technical, unsupported and unverified exclusions cannot be removed. `pending_reclassifications(limit=2000)` provides exact references across all retained learner evidence for the integration to reload from the immutable review journal; missing originals remain pending. `reclassify(rows)` upgrades a bounded batch in one transaction with one final selection calculation. An invalid supplied row aborts the complete batch; the caller omits missing originals. Each upgraded occurrence receives an old/new classification receipt, without adding a rejection or altering an operator decision. `classification_history` exposes those receipts, and cached status reports version, pending references and migration count. A changed same-version grade is still a conflict, not a reclassification.

The outcome ledger is bounded to 4,000 retained attempts. Cohorts keep model, profile, versions, length band and first-versus-repair stage separate. Each cohort counts distinct sources and parents, raw/effective passes, factual/rhyme/target failures, and validated same-family repair pairs. Unknown context is visible but excluded from comparisons. Repeated retries of one source do not become independent support.

Every fault family has a fixed baseline reminder and two alternative, source-grounded procedures. Eight distinct sources across two parents with persistent comparable failures can start the next procedure as **exploring**, not improved. A tested recipe is marked **supported** only after sufficient matched observations show lower target failures, higher effective passes and no higher factual or rhyme failure rate. This is observational support, not causal or semantic proof. Failed recipes advance through a bounded sequence and end as **exhausted** instead of looping indefinitely. A different model/profile/stage cannot reset or promote an in-flight comparison. Base factual and rhyme requirements remain in the immutable production prompt even when an optional recipe is exhausted.

Rollback keeps the historical wording and pauses automatic changes; explicit resume remains required. Individual approvals/kept cuts retain their separate existing influence, while batch approval does not train the learner. The root integration owns collection from actual newly generated outcomes, exposing status in the workbench, and deployment. No live effectiveness improvement is claimed by the module's isolated tests.

## Validation and remaining measurement

The focused test set covers scope fairness, replacing a full incumbent set with stronger current evidence, changed-source fault families, immutable attempt identity, ignored nonproduction events, distinct-source denominators, comparable exploration, guarded support, bounded exhaustion, mismatched contexts, linked repairs and rollback. Existing settings, operator decisions, read-only readers, bounded prompt size and history tests remain in place.

Fifty-two focused module and actual-app integration tests pass with isolated data. Coverage includes classification migration, atomic bulk failure, immutable-evidence conflicts, protected exclusions, retained decisions, bounded reference batches and unversioned legacy records. The real refresh test retrieves exact old occurrences outside the latest 200 summaries, leaves a missing original pending and preserves the review journal and operator note without model, recovery or playback calls. Independent source review found no blocker in selection, outcome/recipe logic, migration, or the production model/grade ticket hooks. A pinned recipe deliberately does not claim automatic retuning across a changed model/profile; unmatched evidence is reported separately and cannot certify the recipe.

The original synchronous `outcome` cost at 4,000 retained outcomes and 2,000 evidence rows measured a median 191.65 ms and maximum 220.51 ms over ten synthetic temporary-database calls. The final implementation reuses aggregates within one transaction and JSON decoding only after comparing every row's current database body. The same-size check measured median 49.85 ms, maximum 66.26 ms, and median CPU time 44.99 ms; 2,000-row bulk reclassification took 107.46 ms with no prompt revision when only the classifier version changed. These are bounded synthetic timings, not latency guarantees. The source hash and individual times are in `prompt-learning-outcome-cost-after.json`; `tools/prompt-learning-cost-check.py` reproduces the temporary-only measurement. Cache tests cover changed database bodies and retention pruning.

After deployment, report first-pass and same-family repair results by the pinned model/profile/prompt/contract/strategy cohort, including denominators and warm-up state. An overall rejection count alone cannot show whether the change helped: backlog imports, repeated attempts, new material and stricter or corrected graders change that count independently. Unsupported or unmeasured cases should remain labeled as such.
